# Переменные Homefash не доезжают до сервера

**Тип:** `fix(ci)`
**Статус:** в работе

## Что нужно сделать

После выкладки интеграции с Homefash кнопка отправки на рабочем сервере отвечала ошибкой «Заказ … нельзя отправить: не задан HOMEFASH_SUPPLIER_ID», хотя значение в панели переменных было заполнено.

## Что оказалось

Приложение читает настройки из `.env` рядом с `app.js` (`require('dotenv').config()` в `app.js`, разбор — `lib/config.js` и `lib/services/homefash/config.js`). На сервере этот файл не ведут руками: его целиком собирает шаг `Create .env from GitHub Secrets and Variables` в `.github/workflows/main.yml`, строка за строкой, из `vars.*` и `secrets.*`. Дальше FTP-шаг заливает файл вместе с кодом, а SSH-шаг пересоздаёт процесс PM2.

Ключевое свойство этого шага: он не копирует всё окружение, а перечисляет переменные поимённо. Заведённое в GitHub значение, для которого нет строки `echo`, остаётся внутри сборки и в рантайм не попадает.

Строк `HOMEFASH_*` в шаге не было — блок добавили в `.env.example` и в локальный `.env`, а про выкладку забыли. Поэтому на сервере не было ни одной переменной интеграции.

Диагностику сбивали две детали:

- `.env` на сервере датирован маем, хотя выкладка была накануне. Это нормально: `FTP-Deploy-Action` синхронизирует только изменившиеся файлы, а содержимое `.env` с мая не менялось.
- `pm2 jlist` не показывает переменные, которые процесс прочитал сам через `dotenv`, — там видно только то, что передал PM2. По одному этому выводу нельзя судить, видит приложение настройки или нет.

Ошибка указывала именно на `HOMEFASH_SUPPLIER_ID`, потому что это первая проверка, которая опирается на окружение. Номер клиента к тому моменту уже брался из базы (`users.code_kb`), поэтому до него претензий не было.

## Решение

В шаг сборки `.env` добавлен блок `HOMEFASH_*`. Ключ API берётся из секретов — он маскируется в логах; остальное из переменных, их удобнее править и видно значение.

Переменные, у которых в коде есть разумные значения по умолчанию (адрес API, заголовок ключа, таймаут, поле номера клиента, пересчёт валюты, список логинов), в выкладку не вносились: чем короче список, тем меньше мест, где можно ошибиться.

`HOMEFASH_DRY_RUN` в список включён намеренно, хотя по умолчанию он и так включает тестовый режим. Причина в том, как это читается: если переменной в GitHub нет, строка уедет пустой, а пустое значение не равно `false` — отправка молча останется тестовой, и выглядеть это будет как «опять не работает».

`HOMEFASH_FALLBACK_CUSTOMER_ID` в выкладку не добавлен сознательно. Это заглушка на время тестов, когда у дилера не был заполнен `code_kb`. Теперь номер есть в базе, а отсутствие заглушки на проде защищает от тихой отправки заказов под чужим номером, если у другого дилера поле окажется пустым.

## Что стоит уточнить

- Проверить, что в GitHub заведены `HOMEFASH_API_KEY` (секрет), `HOMEFASH_SUPPLIER_ID`, `HOMEFASH_SUPPLIER_NAME`, `HOMEFASH_OFFER_VAT_RATE`, `HOMEFASH_OFFER_PREFIX` и `HOMEFASH_DRY_RUN` (переменные). Пустая переменная хуже отсутствующей: она затирает значение по умолчанию.
- После выкладки убедиться по логам PM2, что отправка идёт в нужном режиме: в тестовом в лог уходит `[homefash] DRY RUN POST …` и payload целиком, в боевом — только `POST` и код ответа.
- Когда закончится тестирование, убрать `[TEST]` из `HOMEFASH_OFFER_PREFIX`, иначе партнёр продолжит считать заказы тестовыми.
